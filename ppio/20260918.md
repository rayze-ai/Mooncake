# 机架感知（Rack Affinity）部署方案：4 × GB300 NVL72

## 1. 集群拓扑与带宽事实

| 层级 | 规模 | 互联 | 单向/双向带宽 |
| --- | --- | --- | --- |
| 机架内（NVLink 域） | 18 台 compute tray / 72 GPU / 36 Grace CPU / 9 NVSwitch tray | NVLink 5（MNNVL） | 1.8 TB/s per GPU，整机架 all-to-all 130 TB/s |
| 机架间 | 4 个机架 = 72 节点 / 288 GPU | RDMA（IB 或 RoCE，ConnectX-8） | 800 Gb/s ≈ 100 GB/s per port |

关键比例：**机架内 NVLink 带宽约为跨机架 RDMA 的 18 倍**。这是本方案全部收益的来源，也是「写入必须留在本机架」的唯一理由。

一个 NVL72 机架就是一个 NVLink 域（一个 IMEX domain）。因此本文中 `rack_id` 与 NVLink 域是**同一个概念**，不要把它理解成物理机柜位置。

## 2. 目标

- **Prefill 写入**：KV cache 写入 Mooncake Store 时走 NVLink；master 只在同机架的 store 节点上分配副本。
- **Decode 读取**：优先读同机架副本（NVLink），跨机架副本也必须可读（RDMA），不能因为副本在别的机架就失败。

换句话说，写入侧是**硬约束**（strict），读取侧是**软偏好**（preference + fallback）。

## 3. 当前实现状态

本分支（`yaochen/topology-aware`）已经把机架信息打通成一条完整链路：

```
配置 rack_id
  → Client::SetRackAffinity()
  → Segment.rack_id（mount 时携带）
  → master: RackSegmentIndex（segment name → rack_id）
  → BufferAllocatorBase::SetRackId()
  → AllocatedBuffer::Descriptor::rack_id_（副本描述符）
  → reader: SelectBestReplica(..., local_rack_id)
```

### 3.1 写入侧（master 放置）

`MasterService::AllocateReplicas` 有两种模式：

- **strict 模式**（`strict_rack=true` 且 `rack_id` 非空）：把所有非本机架 segment 放入 `excluded_segments`。本机架放不下时返回 `NO_AVAILABLE_HANDLE` 并触发淘汰，**不会**溢出到其他机架。
- **soft 模式**（只设 `rack_id`）：把同机架 segment 追加进 `preferred_segments`，排在 host-local 之后、其他机架之前；本机架满了仍可跨机架落盘。

`strict_rack=true` 但 `rack_id` 为空时打 WARNING 并退回非 strict，不会静默改变行为。

### 3.2 读取侧（副本选择）

`SelectBestReplica` 的优先级（`replica_selection.h`）：

```
local MEMORY  >  local NOF_SSD  >  同机架 MEMORY  >  远端 MEMORY  >  远端 NOF_SSD  >  LOCAL_DISK  >  DFS  >  DISK
```

三点需要注意：

1. **同机架层位于 local 之后**。特别是「本地 NOF_SSD 仍然优先于同机架 MEMORY」——这一条沿用了机架感知之前的既有行为，本次没有改动。如果希望同机架 NVLink DRAM 读优先于本地 SSD 读（在 GB300 上这是合理的，NVLink DRAM 约 900 GB/s 量级 vs 本地 NVMe 约 10 GB/s 量级），需要另行决策并单独改动。
2. **没有 rack_id 的副本被视为远端**。因此老 master 或未配置 rack 的节点行为完全不变。
3. **`local_rack_id` 为空时逐字节等价于历史行为**，机架感知是纯 opt-in。

评分机制（issue #2516）只在**远端**副本之间排序，不会把跨机架副本提到同机架副本之前。

## 4. 可行性分析

必须把问题分成两层看，结论不同。

### 4.1 放置层（Mooncake Store）：可行，已实现

master 的同机架选点、reader 的同机架优先、跨机架 fallback，全部可以按第 3 节的语义工作。这一层没有阻塞问题。

### 4.2 传输层（Transfer Engine）：**这是真正的阻塞点**

`MultiTransport::selectTransport` 依据**目标 segment 发布的 protocol** 选择 transport，**没有任何 NVLink 域可达性判断**。具体有三个问题：

**问题 1：transport 安装是互斥的。**
`transfer_engine_impl.cpp` 里是一条 if/else 链：设置 `MC_FORCE_MNNVL`（或检测不到 HCA）就装 `nvlink`，否则装 `rdma`。**一个客户端只会装其中一个**，不会两个都装。

**问题 2：`nvlink` 没有跨机架 fallback。**
对于 `hip` / `musa` / `shm` 这类只能本机 IPC 的协议，代码里有 `isLocalIpcReachableTarget()` 门控，跨主机时自动跳过并退到 rdma。**`nvlink` 不在这个名单里**。所以一个以 `nvlink` 协议发布的 segment，被其他机架的 reader 选中时，会直接去走 NVLink——而跨机架没有 NVLink 通路，fabric handle 导入会失败，**不会自动退回 RDMA**。

**问题 3：多协议 segment 当前也解决不了。**
理论上可以让 segment 同时发布 `"nvlink,rdma"`，但：
- `ENABLE_MULTI_PROTOCOL` 默认 **OFF**（`mooncake-common/common.cmake`）。
- 即使打开，`protocol_priority()` 里 **没有 `nvlink` 条目**，落到默认值 `0`，而 `rdma` 是 `2`。也就是说 rdma 永远胜出，**NVLink 永远不会被选中**。

**结论：机架感知的放置策略是必要条件，但不是充分条件。** 仅靠本分支的改动，无法实现「prefill 写走 NVLink、decode 跨机架退 RDMA」。要让 NVLink 真正进入数据路径，还需要在 transfer engine 侧补齐：

1. 在 `protocol_priority()` 中加入 `nvlink`，且优先级高于 `rdma`。
2. 为 `nvlink` 增加**机架/NVLink 域可达性门控**（类比 `isLocalIpcReachableTarget`，但判据是 rack_id/clique 而非 hostname），跨域时跳过 nvlink buffer 退到 rdma。
3. store 节点以多协议 `"nvlink,rdma"` 注册 segment，并开启 `ENABLE_MULTI_PROTOCOL`。
4. **让 segment 真正被导出到 NVLink fabric**。这是最底层的一道坎，详见 4.3。


### 4.3 更底层的问题：当前没有任何 Store 配置能把 segment 导出到 MNNVL fabric

`NvlinkTransport::registerLocalMemory` 在 fabric 模式下（`use_fabric_mem_`，所有设备支持 fabric 时的默认值）先调 `cuMemRetainAllocationHandle(addr)`。**如果这块内存不是 `cuMemCreate` 分配的，它打一条 WARNING 然后 `return 0` —— 什么都不注册**，日志写的是「can be used as local buffer」，也就是说这块 buffer 根本没有进入 fabric，远端节点无法通过 NVLink 访问。

对照 Store 的两条分配路径：

| Store 配置 | segment 内存来源 | 能否导出 fabric handle |
| --- | --- | --- |
| 默认 | host DRAM：`aligned_alloc` / numa / hugepage mmap | **不能** —— 非 `cuMemCreate`，`cuMemRetainAllocationHandle` 失败 |
| `USE_VRAM_SEGMENT=ON` + `protocol=nvlink` | 默认 `cudaMalloc`；设 `MC_STORE_VRAM_FABRIC=1`（需 `USE_MNNVL`）后走 `cuMemCreate` | 默认**不能**；开开关后**能**，见第 9 节 |
| `USE_VRAM_SEGMENT=ON` + `protocol=nvlink_intra` | `allocateFabricMemory_intra()`，宏展开为 `IntraNodeNvlinkTransport::allocatePinnedLocalMemory()` | **不能** —— 名字里有 Fabric，实现却是纯 `cudaMalloc`（日志原话 “memory will NOT be exportable”）。该协议靠 `cudaIpcGetMemHandle` 工作，跟 fabric handle 是两套机制，且仅限单机 |

也就是说：**改动前，Store 三条分配路径没有任何一条会产生 fabric handle**。想让同机架跨机 NVLink 生效，除了 4.2 的四项，还必须改 Store 的分配路径本身——host DRAM 走 EGM（路线 B，见 8.3），或让 VRAM segment 在 `protocol=nvlink` 下也走 `cuMemCreate` + `CU_MEM_HANDLE_TYPE_FABRIC` 导出。

**后者已实现**（第 9 节）：`MC_STORE_VRAM_FABRIC=1` 打开后，`protocol=nvlink` 的 VRAM segment 走 fabric 分配，`cuMemRetainAllocationHandle` 不再失败。但**这只解决了分配侧**；8.4 的选路层若不改，请求依然到不了 NVLink transport。IMEX domain 仍需在真实 NVL72 上验证。

## 5. 配置方案

### 5.1 rack_id 规划

4 个机架分别为 `rack0` … `rack3`。同一个 NVL72 机架内的全部 18 台节点必须使用**相同**的 `rack_id`。

三种配置入口（任选其一，优先级：配置文件 > 环境变量）：

```jsonc
// mooncake.json
{
  "local_hostname": "node-r0-03",
  "metadata_server": "P2PHANDSHAKE",
  "master_server_address": "10.0.0.1:50051",
  "protocol": "rdma",
  "rack_id": "rack0",
  "strict_rack": true
}
```

```bash
export MOONCAKE_RACK_ID=rack0
export MOONCAKE_STRICT_RACK=true
```

`rack_id` 必须在 mount segment **之前**设置好（`SetRackAffinity` 在 `setup_internal` 中于建 client 之后、mount 之前调用），否则 segment 带不上机架身份。

### 5.2 Prefill 节点（写入侧：strict）

```bash
export MOONCAKE_RACK_ID=rack0        # 按所在机架填
export MOONCAKE_STRICT_RACK=true     # 写入不允许跨机架
```

语义：master 只在 rack0 的 store 节点上分配副本；rack0 容量不足时触发淘汰并返回 `NO_AVAILABLE_HANDLE`，**不会**写到 rack1-3。

注意副本数约束：`strict_rack=true` 时，`replica_num` 不能超过**本机架**可服务 segment 数。否则分配必然失败。

### 5.3 Decode 节点（读取侧：软偏好）

```bash
export MOONCAKE_RACK_ID=rack0        # 按所在机架填
export MOONCAKE_STRICT_RACK=false    # 或直接不设
```

语义：`SelectBestReplica` 优先挑 rack0 的副本；rack0 没有时读其他机架（RDMA）。decode 侧**不要**开 strict——strict 只影响写入放置，但把它开在 decode 上没有收益，且会在 decode 自身也做写入（如 chunked prefill 回填）时意外限制放置。

### 5.4 Mooncake Store 节点

store 节点自身也要配 `rack_id`（它 mount 的 segment 靠这个字段进入 master 的 `RackSegmentIndex`）。**这是整套机制的数据来源，不能省。**

```bash
export MOONCAKE_RACK_ID=rack0
# store 节点不需要 strict_rack，它不是写入方
```

### 5.5 NVLink 相关（见 4.2 / 4.3，当前需代码改动才生效）

```bash
# 目标状态，依赖 4.2 的改动落地后才有效
export MC_ENABLE_MNNVL=1     # 选用 TENT mnnvl transport
export MC_MNNVL_EGM=1        # 允许 NVLink 访问 host DRAM（EGM）
```

并且 buffer 必须用 `allocateLocalMemory("cpu:<numa>")` 分配才会被导出为 fabric handle；普通 `cudaHostRegister` / `aligned_alloc` / `cudaMalloc` 的内存都只能走 RDMA/TCP。上面两个变量针对的是 host DRAM（EGM，路线 B，未实现）。

VRAM segment 的 fabric 分配已实现，用下面这个开关（详见第 9 节）：

```bash
# 需要编译期 USE_VRAM_SEGMENT=ON + USE_MNNVL=ON，且 protocol=nvlink
export MC_STORE_VRAM_FABRIC=1
```

取值按布尔解析（`1/true/yes/on/enable` 开，`0/false/no/off/disable` 关）。
注意它与 `MC_STORE_USE_HUGEPAGE` 的语义**不同**：后者「存在即生效」，
设成 `0` 也算开；前者设成 `0` 就是关。不设、值非法、或编译期开关缺失时
都保持历史 `cudaMalloc` 行为（后两种会打 WARNING）。

另外 NVLink 节点上**不能**设 `MC_STORE_USE_HUGEPAGE`，否则分配会在到达
VRAM 路径之前被 hugepage 路径截走，见 8.2 A4。

### 5.6 Master

master 无需机架配置，它从各 segment 的 `rack_id` 自动建立索引。建议打开 `VLOG(1)` 观察放置决策：

```
key=..., rack_id=rack0, strict_rack_excluded=54, rack_serving_segments=18
key=..., rack_id=rack0, rack_preferred_segments=18
```

## 8. 支持 fabric handle 的改造计划

### 8.1 结论先行

不需要新写 CUDA 代码。`NvlinkTransport::allocatePinnedLocalMemory()`
（`nvlink_transport.cpp:1184`，`static`、public）已经把完整的 fabric 分配流程实现好了：
`cuMemGetAllocationGranularity` → `cuMemCreate`(`CU_MEM_ALLOCATION_TYPE_PINNED` +
`CU_MEM_LOCATION_TYPE_DEVICE` + `CU_MEM_HANDLE_TYPE_FABRIC`) → `cuMemAddressReserve`
→ `cuMemMap` → `cuMemSetAccess`，并在 `!supportFabricMem()` 时回落 `cudaMalloc`。
导入侧（`cuMemImportFromShareableHandle`）在同一个文件里也已具备。

所以主体工作是**换调用点 + 打通选路**，不是实现 fabric。

已核实的前置事实：

- mount 会注册到 transport：`Client::MountSegmentAndGetId`（`client_service.cpp:3831`）
  → `TransferEngineImpl::registerLocalMemory`（`transfer_engine_impl.cpp:759`）
  **对 `listTransports()` 里每一个 transport 都调一次**。链路本身没问题。
- 失败点在分配：`registerLocalMemory` fabric 分支的
  `cuMemRetainAllocationHandle`（`nvlink_transport.cpp:997`）对非 `cuMemCreate`
  的内存失败后 **`return 0`**——注册「成功」但什么都没注册，mount 不报错，
  远端却永远拿不到这块 buffer。这是最需要注意的一点：**它是静默的**。
- `supportFabricMem()` 是文件内 `static`（`nvlink_transport.cpp:569`），
  Store 侧无法直接调用，只能依赖 `allocatePinnedLocalMemory` 内部的回落。

### 8.2 路线 A：VRAM segment + fabric（推荐先做）

> **状态：A1–A3 已实现，带开关。** 见第 9 节。A4 是部署约束，不是代码改动，仍然成立。
> 下面保留原始分析，作为改动动机的记录。

改动集中在 `mooncake-store/src/common/client_buffer_allocation.cpp`。

**A1. 分配路径**：`allocate_vram_memory()`（第 30 行）当前在 `protocol == "nvlink"`
时落到第 50 行的 `cudaMalloc`。改为调用
`NvlinkTransport::allocatePinnedLocalMemory(total_size)`（需要 `USE_MNNVL` 编译开关
与对应 include）。`nvlink_intra` 分支保持不变。

**A2. 对齐（必须处理，否则 cachelib 会挂）**：Store 要求按
`facebook::cachelib::Slab::kSize` 对齐，即 `1 << 24` = **16 MB**
（`cachelib_memory_allocator/Slab.h:82,88`）。而 `allocatePinnedLocalMemory` 把
`granularity`（Blackwell 上通常 2 MB）直接当作 `cuMemAddressReserve` 的 alignment
参数（`nvlink_transport.cpp:1236`），**只保证 2 MB 对齐**。两种做法：

- 给 `allocatePinnedLocalMemory` 增加一个 alignment 形参，
  用 `std::max(granularity, alignment)` 去 reserve；或
- 在 Store 侧多申请 `Slab::kSize` 并自行向上取整返回地址——但那样
  `free` 时必须保留原始指针，代价更大。

推荐第一种。同时注意它内部会把 `size` 向 granularity 取整
（第 1229 行），实际映射量可能大于 Store 认为的 `total_size`。

**A3. 释放路径（现有潜在 bug）**：`free_memory()`（第 133 行）在
`USE_VRAM_SEGMENT` 下只看 `USE_INTRA_NVLINK` 决定调
`freeFabricMemory_intra` 还是 `cudaFree`，**完全不看 protocol**。
今天两者都是 `cudaFree` 所以无害；一旦 A1 落地，`nvlink` 的内存变成
`cuMemCreate` 分配，再走 `cudaFree`/`cudaFree`-等价路径就会泄漏
（`cuMemUnmap` + `cuMemRelease` + `cuMemAddressFree` 都不会执行）。
必须让 `free_memory` 按 protocol 分支到
`NvlinkTransport::freePinnedLocalMemory`。

**A4. 确保这条分支真的走得到**：`real_client.cpp:1091` 的优先级是
`numa segments` > `ascend/ubshmem` > `hugepage` > `allocate_buffer_allocator_memory`。
只有最后一条能到 VRAM。所以 NVLink 节点上**不能**设
`MC_STORE_USE_HUGEPAGE`（注意它是「存在即生效」，设成 `0` 也算开），
且不能触发 NUMA 分段（`protocol=="rdma"` 且多 NIC NUMA 才触发）。

### 8.3 路线 B：host DRAM + EGM（更大，可后置）

如果要让 host DRAM 的 segment 也能被 NVLink 访问，需要
`CU_MEM_LOCATION_TYPE_HOST_NUMA` 的 fabric 分配。TENT 里已经有实现：
`tent/src/transport/mnnvl/mnnvl_transport.cpp` 的 `buildEgmAllocationProp()`
（配合 `isEgmAllocation()` / `findDeviceOnNuma()`）。两种接法：

- 把 `buildEgmAllocationProp` 提取到 Store 可调用的位置；或
- 让 Store 走 TENT 的 `allocateLocalMemory`（`tent/include/tent/transfer_engine.h:289`），
  该 API **classic `TransferEngine` 上不存在**，等于把 Store 绑到 TENT 路径。

额外依赖：驱动侧开 EGM、`MC_ENABLE_MNNVL=1` + `MC_MNNVL_EGM=1`，
且 copy 要在属主 socket 的 GPU 上发起（TENT 注释指出 C2C 链路限制）。

### 8.4 选路层（不改则前面全部白做）

即使 buffer 成功导出 fabric handle，当前仍然到不了 NVLink：

1. **transport 安装是排他的 if/else**（`transfer_engine_impl.cpp:410-454`）：
   `MC_INTRANODE_NVLINK` → 只装 `nvlink_intra`；否则
   `force_mnnvl || (无 HCA && 未设 MC_FORCE_HCA)` → 只装 `nvlink`；否则装 `rdma`。
   GB300 + ConnectX-8 一定检测到 HCA，所以默认只有 RDMA；而设了
   `MC_FORCE_MNNVL` 就只有 NVLink、**跨机架 decode 直接没有 RDMA 可回落**。
   必须改成两者并存。
2. **`ENABLE_MULTI_PROTOCOL` 默认 OFF**（`common.cmake`），需要打开，
   segment 以 `"nvlink,rdma"` 双协议注册。
3. **`protocol_priority()` 没有 nvlink 分支**（`multi_transport.cpp:615-627`），
   落到 `return 0`，低于 rdma 的 2 ——永远选不到 NVLink。需加
   `if (p == "nvlink") return 5;`（高于 rdma），并配一个 `MC_DISABLE_MNNVL` 逃生开关，
   与 hip/maca/musa 的写法保持一致。
4. **需要机架可达性门控**。`isLocalIpcReachableTarget()` 只处理
   `hip`/`musa`/`shm`，nvlink 不在其中。NVLink 的可达范围是「同一 NVLink domain /
   IMEX domain」，正好等于我们的 `rack_id`。需要把 nvlink 纳入同类门控：
   目标不同机架时跳过它的 nvlink buffer、回落 rdma。
   这一步能直接复用本次已落地的 `rack_id`。

### 8.5 建议顺序

| 阶段 | 内容 | 可验证的现象 | 状态 |
| --- | --- | --- | --- |
| 1 | 8.4 的第 3、4 项（选路 + 机架门控） | 单测可覆盖，不需要 NVL72 | 未做 |
| 2 | A1–A3（分配/释放/对齐） | 日志不再出现 “is not allocated by cuMemCreate” | **已实现**，见第 9 节 |
| 3 | 8.4 第 1、2 项（双 transport 并存） | 同机架走 nvlink、跨机架走 rdma | 未做 |
| 4 | 真机验证 | 见 8.6 | 待做 |
| 5 | 路线 B（EGM，按需） | host DRAM segment 也能 NVLink 访问 | 未做 |

注意阶段 2 已经先于阶段 1 落地（按要求先实现 fabric 分配）。这意味着
**开关打开后，跨机架仍可能误选 NVLink**——阶段 1 的机架门控还没做。
在 8.4 的选路项落地前，这个开关只应在同机架范围内验证。

阶段 1 单独就有价值：它让「跨机架不会误选 NVLink」这件事变得安全，
是后面几步的前提。

### 8.6 必须在真机上验证的项

- `CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED` 在全部 GPU 上为真
  （否则 `supportFabricMem()` 返回 false，静默回落 `cudaMalloc`）。
- IMEX domain 覆盖整个 NVL72 机架的 18 个节点，且与 `rack_id` 划分一致。
- `cuMemGetAllocationGranularity` 的实际取值（决定 A2 的对齐处理）。
- 未设 `MC_USE_NVLINK_IPC`（一旦设置，`supportFabricMem()` 直接返回 false）。
- 跨机架 get 确实回落 RDMA 而不是报错。

## 9. fabric handle 分配的实现（本次改动）

### 9.1 开关

```bash
export MC_STORE_VRAM_FABRIC=1    # 默认关闭
```

取值语义是**按值判断**，不是「存在即生效」（区别于 `MC_STORE_USE_HUGEPAGE`）：

| 取值 | 结果 |
| --- | --- |
| `1` / `true` / `yes` / `on` / `enable`（大小写不敏感，允许首尾空格） | 开启 |
| `0` / `false` / `no` / `off` / `disable` | 关闭 |
| 空字符串、`maybe` 等无法解析的值 | 关闭 + `LOG(WARNING)` 回显原值 |
| 未设置 | 关闭 |

之所以不用「存在即生效」：`MC_STORE_VRAM_FABRIC=0` 若被当成开启，
选中的失败模式恰好是 4.3 里那个「注册成功但什么都没注册」的静默故障，
要等到远端读不到数据才暴露。宁可让开关本身难以误开。

生效条件（三者同时满足）：`USE_VRAM_SEGMENT=ON` + `USE_MNNVL=ON`（且不与
`USE_HIP`/`USE_MUSA`/`USE_UBSHMEM` 同时开）+ `protocol == "nvlink"`。
`nvlink_intra` 不受影响，仍走 CUDA IPC。

**若开关已设但当前编译组合无法支持，会打一条 WARNING 明确说明
「即将回落 cudaMalloc，该 segment 不会被其他节点通过 NVLink 访问」**，
而不是静默忽略。这是本功能存在的理由，因此不允许它自己制造同类静默。

### 9.3 对齐处理（A2）

原实现把 `granularity`（通常 2 MB）直接当作 `cuMemAddressReserve` 的
alignment，只保证 2 MB；而 cachelib 要求 `Slab::kSize` = 16 MB。
新重载取 `max(granularity, alignment)`：

- 两者都是 2 的幂时，较大者必然是较小者的整数倍，
  因此按较大者向上取整的 `size` 仍满足 `cuMemCreate` 的 granularity 要求；
- 万一不是 2 的幂（防御性分支），退回 `granularity` 并告警，不静默放宽；
- 单参数重载等价于 `alignment = 0`，行为与改动前完全一致。

非 fabric 回落路径（`!supportFabricMem()`）用的是 `cudaMalloc`，
无法接受任意 alignment；此时若返回地址不满足请求的对齐，会打 WARNING
说明原因，而不是假装成功。

### 9.4 释放路径（A3，顺带修掉的隐患）

改动前 `free_memory()` 在 `USE_VRAM_SEGMENT` 下只看编译开关
`USE_INTRA_NVLINK`，**完全不看 protocol**。当时两个分支都是 `cudaFree`，
所以无害；但 A1 一落地，`cuMemCreate` 的内存走 `cudaFree` 就会同时泄漏
物理 handle 和保留的 VA 区间（`cuMemUnmap`/`cuMemRelease`/`cuMemAddressFree`
都不会执行）。

现在 `free_memory()` 与 `allocate_vram_memory()` 用**同一个判定函数**
（`use_fabric_vram()`）分支，且该函数把环境变量读一次后缓存
（函数内 `static`），保证同一块内存的分配与释放不会因为中途改环境变量
而选到不同的释放器。
