KV 走 NVLink 的四个判据

判据不是「显存还是 DRAM」，而是这块内存有没有被 VMM 分配并导出到 fabric 地址空间。 下面按你的四个问题逐层拆开：谁需要 fabric 分配、DRAM 能不能走、写路径怎么走、读路径怎么走。

判据

能不能走 NVLink，只看两件事

顺序固定，第一问不过就没有第二问。注意两问里都没有出现「显存还是 DRAM」。

1
源和目标在同一个 NVLink domain 吗？
NVL72 一个机架 = 一个 NVLink domain = 一个 IMEX domain（18 节点 / 72 GPU）。 这是物理边界，软件绕不过去。
同 domain → 进入第 2 问 跨 domain → 只能 RDMA / RoCE，无第二选择
2
这块内存导出到 fabric 了吗？
要求是 cuMemCreate + CU_MEM_HANDLE_TYPE_FABRIC 的 VMM 分配。 远端要访问，需要稳定物理后备、进 fabric 可见页表、拿到可导入的句柄。
已导出 → NVLink 未导出 → RDMA
内存来源能否导出 fabric handle为什么
aligned_alloc / numa / hugepage mmap
Store 今天的默认路径		 不能 不是 VMM 分配，cuMemRetainAllocationHandle 认不出来
cudaHostRegister 的 pinned DRAM 不能 pin 服务的是 DMA 引擎，跟 fabric 导出是两条正交的事
cudaMalloc 的显存 不能 显存也不行。判据是分配方式，不是内存位置
cuMemCreate + HANDLE_TYPE_FABRIC
location = DEVICE		 能 显存走 fabric 的正路，本分支已实现
cuMemCreate + HANDLE_TYPE_FABRIC
location = HOST_NUMA（EGM）		 能 host DRAM 走 fabric 的正路，见下一节

所以「Mooncake 用 pinned DRAM 所以用不了 NVLink」

结论在今天的默认配置下是对的，但判据是错的。 走不通的原因不是「它用 DRAM」，而是「它的分配器没走 VMM fabric 路径」。 判据错会导致后续决策跑偏——比如以为「把数据搬到显存就能走 NVLink」，实际上 cudaMalloc 的显存同样导不出去。

问题 2

DRAM 能走 NVLink 吗？能，但要两个条件同时成立

NVLink 是内存语义互连，传的是 load / store / atomic，跑在一个物理地址空间上。 链路本身不关心目标物理页是 HBM 还是 DRAM。

条件x86 + PCIe 挂 GPU（传统 HGX）Grace-Blackwell（NVLink-C2C）
条件一
host DRAM 物理上在 NVLink fabric 上吗		 否
NVLink 只连 GPU↔GPU，DRAM 在 PCIe / DDR 一侧，fabric 里根本不存在这条边		 是
LPDDR 被拉进 GPU 可寻址的相干地址空间
条件二
这块内存映射/导出到 fabric 了吗		 两种形态都要满足。有资格 ≠ 可达：需要 CU_MEM_LOCATION_TYPE_HOST_NUMA 的 fabric 分配，也就是 EGM

这跟 CPU 指令集无关。反例是 POWER9 + Volta（IBM AC922），CPU↔GPU 之间就是 NVLink 2.0。 真正的判据是「CPU 侧有没有实现一条与 GPU 相干的 NVLink 级端口」——Intel / AMD 没有，Grace 有。

EGM 在 TENT 里已经实现了

mnnvl_transport.cpp:70 的 buildEgmAllocationProp()， prop.location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA。 它的注释直接点名了这个场景：host-resident 数据（例如 CPU 侧的 KV cache） 「moves over NVLink instead of the NIC」。

但 Store 没接这条路。classic nvlink_transport 里 HOST_NUMA 出现 0 次，三处 CU_MEM_LOCATION_TYPE 全是 DEVICE （:1128, :1232, :1294）。

带宽序关系：通了也不等于满速

DRAM-over-NVLink ≠ HBM-over-NVLink。瓶颈在网关之后： 远端 GPU → NVSwitch → 目标节点 GPU → C2C → Grace → LPDDR。

本地 HBM > HBM over NVLink > DRAM over NVLink >> DRAM over RDMA

关键是最后那个 >>：DRAM-over-NVLink 拿不到满带宽， 但相对跨机架 RDMA 仍有接近一个数量级的收益。

问题 3

P 写 KV：谁需要 fabric 分配

先纠一个容易搞反的点：需要 fabric 分配的不是 P 自己的 buffer，而是被访问的那一侧—— Store segment 的内存。 P 读自己的本地 buffer 不需要跨节点句柄；要跨节点被访问的是目标。

「同机架」就够，不需要「同机器」

MNNVL 的 fabric handle 本来就是为跨节点导入设计的，同机架不同节点照样走 NVLink。 要求「同机器」会把可用范围从 18 台压到 1 台。

只有 nvlink_intra 协议才需要同机器——它靠 cudaIpcGetMemHandle， 跟 fabric handle 是两套独立机制。这是两个不该混淆的东西。

跨 domain 的现状比「未实现」更糟

在 nvlink 协议下跨机架不是退化成 RDMA，而是直接失败。 transport 安装是排他 if/else（transfer_engine_impl.cpp:410-454）， 设了 MC_FORCE_MNNVL 的节点根本没装 rdma，没有东西可回落。

isLocalIpcReachableTarget() 的门控名单只有 hip / musa / shm，nvlink 不在里面，所以跨机架也不会被跳过。 生产节点一律不要设 MC_FORCE_MNNVL。

所以两条目标需求都还没达成

前三层都通了，但它们只决定「KV 落在同机架、并且那块内存有资格走 NVLink」。 「有资格」和「真的会走」之间差的就是选路层，而选路层是零。 fabric 导出成功了，数据照旧从 RDMA 走。

另外注意当前是「分配层先于选路层落地」：fabric 分配已实现、门控未实现。 所以 MC_STORE_VRAM_FABRIC 目前只应在隔离节点上验证， 不要在跨机架流量存在的生产环境打开。

追问 1

IMEX 作用在哪一层

简短回答：IMEX 在所有这些之下，是节点级的系统设施，不属于 TP／DP／KV 传输中的任何一层， 也不在 P 或 D 的内部。Mooncake 启动时不需要、也无法「开启」它——它必须在 Mooncake 起来之前就已经由运维配好并运行。

问题答案
作用于跨机 TP 还是跨机 DP？ 两者都不是，也两者都是。IMEX 不区分上层用途——它只管「这两个节点之间能不能导入 fabric 句柄」。跨机 TP、跨机 DP、Mooncake 的 KV 传输共用同一个 IMEX domain，不是各自一份。
在 P 或 D 的内部吗？ 不在。它是节点级守护进程，与推理进程平级且先于它存在。P 和 D 如果在同一个 NVL72 机架内，它们共享这个 domain。
Mooncake 启动时需要开启吗？ 不需要，也开不了。Mooncake 只是 cuMemCreate 的调用方。IMEX 没配好的表现是分配／导出直接失败，不是 Mooncake 少做了一步初始化。
那 Mooncake 侧要做什么？ 三件事：① 打开 MC_STORE_VRAM_FABRIC=1 走 fabric 分配；② 容器部署时确保 /dev/nvidia-caps-imex-channels 设备节点已透传进容器；③ 保证 MOONCAKE_RACK_ID 的划分与 IMEX domain 边界完全一致。

第 ③ 条是新的风险点，因为门控已定为配置驱动

rack_id 是手填的环境变量，IMEX domain 是运维配的系统设施， 两者没有任何程序化关联——没有代码会去校验它们一致。

如果两个物理机架被填了同一个 rack_id，门控会判定「同 domain，可以走 NVLink」， 然后 fabric 句柄导入失败，而且没有回落。这正是决策 #2 选了配置驱动后 必须补「启动期一致性校验」的原因。

追问 2

选路层为什么没实现

不是「忘了做」或「排期没到」。查过代码后，这里有三个结构性障碍叠加， 每一个单独都能让选路层无从下手。

1
装了 nvlink 就没有 rdma —— transport 安装是排他的
transfer_engine_impl.cpp:405-454 是一条 if / else if / else 链，一次只装一个 transport。 更关键的是它的条件：nvlink 只在 force_gpu_p2p || (no_hca && !force_hca) 时才装—— 也就是「设了 MC_FORCE_MNNVL」或「压根检测不到 HCA」。 有 RDMA 网卡的正常生产节点会走 else if (!no_hca) 装 rdma。
有网卡的节点：只有 rdma，nvlink 没装，选路无从选择 设了 MC_FORCE_MNNVL：只有 nvlink，跨机架无 rdma 可回落
所以「选路」这个动作在今天的架构里没有成立的前提： 两个候选 transport 从来不同时存在。要做选路，得先让它们并存。
2
那段 protocol_priority() 默认根本不编译
它整段在 #ifdef ENABLE_MULTI_PROTOCOL 里，而 common.cmake:193 的默认值是 OFF （本次构建的 CMakeCache.txt 也确认 ENABLE_MULTI_PROTOCOL:BOOL=OFF）。 BufferDesc::protocol 这个字段本身也在同一个 #ifdef 之内。
默认构建里：buffer 上没有 protocol 字段，也没有按 protocol 选路的代码
换句话说，「给 protocol_priority() 加一个 nvlink 分支」这个 最小改法，在默认构建里改的是一段死代码。得连带把 ENABLE_MULTI_PROTOCOL 打开、并把 segment 注册成多协议， 才轮得到选路逻辑生效。
3
TE 看不见 rack_id —— 门控缺少判据来源
决策 #2 定的门控要比较「本地 rack」与「目标 rack」，但 transfer_metadata.h 里搜不到任何 rack 字段 （BufferDesc 只有 name / addr / length / device_id， 外加 #ifdef 里的 protocol 和 MR key）。
rack_id 只活在 Store 层的 Segment 和副本 descriptor 里。门控要在 TE 内部做，而 TE 看不到 Store 的 rack_id。 所以「复用本次已落地的 rack_id」这个说法不成立——必须先把字段打通到 TE 元数据层，这本身是一项独立工作。
今天：TE 无法回答「目标在不在我的 NVLink domain 里」

为什么会形成这个局面：分配层先于选路层落地

fabric 分配（MC_STORE_VRAM_FABRIC）是独立可验证的——单机上就能确认 cuMemCreate 成功、句柄能导出，不需要 NVL72。 而选路层要真正验证，需要多节点同机架 + IMEX domain，门槛高得多。

于是先落地了能验证的那一半。代价是出现一个中间状态： 内存已经导出到 fabric、master 也会挑同机架的 segment， 但数据照旧从 RDMA 走——看起来配置生效了，实际收益为零， 而且不会有任何报错提示你这件事。

要让选路层成立，依次需要能否单测覆盖状态
① 把 rack_id 打通到 TE 元数据层（BufferDesc / segment desc） 可以 未做
② 机架可达性门控：跨 rack 的目标不选 nvlink 可以，不需要 NVL72 未做
③ 打破排他 if/else，让 nvlink 与 rdma 并存 部分 未做
④ 打开 ENABLE_MULTI_PROTOCOL + segment 双协议注册 部分 未做
⑤ nvlink 进 protocol_priority() 可以 未做
⑥ 真机验证：IMEX domain 覆盖、跨机架确实回落 RDMA 否，需 NVL72 未做

建议的顺序是 ② 先做：它让「跨机架不会误选 NVLink」这件事变安全，是后面几步的前提， 而且纯单测可覆盖、不需要 NVL72。③ 是决策 #2 之后从优化升级为必需的一项—— 没有它，配错 rack_id 的后果就是不可用而不是变慢。
