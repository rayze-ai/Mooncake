配套文档，同目录：

- `index.html` —— 总览：架构图、PD 读写路径、各组件构建与配置
- `20260918.md` —— 方案设计与可行性分析（为什么这么做、哪里还不通）
- `build.md` —— 三个组件怎么构建（容器与 wheel 两条路）
- `config.md` —— NVL72 每个组件的完整可抄配置

仓库根下（通用文档，本文不重复）：

- `docs/source/getting_started/build.md` —— 通用编译指南（与同目录 `build.md` 不是一份）

本文只讲这套机架感知方案**怎么编、怎么部、怎么配**，通用部分不重复。

## 0. 先读这一段

本手册覆盖两件独立的事，**收益和成熟度完全不同**，不要混在一起上线：

| 能力 | 状态 | 上线建议 |
| --- | --- | --- |
| **机架感知放置**（写入锁本机架、读取优先同机架） | 已实现，可用 | 可以直接上，收益确定 |
| **NVLink 进入数据路径**（fabric handle） | 分配侧已实现；**选路层未实现** | 只在单机架内做验证，**不要**跨机架启用 |

第二项的关键限制：本次实现了「segment 能导出 fabric handle」，但
`MultiTransport` 的选路层还没有机架可达性门控（`20260918.md` §8.4）。
也就是说**跨机架的请求仍可能选中 NVLink 并失败，且不会自动回落 RDMA**。
所以 `MC_STORE_VRAM_FABRIC=1` 目前只应在单机架范围内验证。

即使完全不启用 NVLink，第一项也值得上：把写入锁在同机架内，
同机架 RDMA 通常只经过一级 leaf 交换机，避免了 spine 跳数和跨机架拥塞。

## 1. 编译

### 1.1 依赖

```bash
# Ubuntu 22.04 LTS+，cmake 3.20.x，gcc 9.4+
sudo bash dependencies.sh
```

需要联网：脚本会装系统包、初始化 submodule、安装 Go。

### 1.2 场景 A：只要机架感知（推荐先用这个）

不需要任何 GPU 相关开关，机架感知是纯放置层逻辑。

```bash
mkdir -p build && cd build
cmake ..
make -j
sudo make install
```

### 1.3 场景 B：机架感知 + fabric handle（NVLink 分配侧）

```bash
mkdir -p build && cd build
cmake .. \
  -DUSE_VRAM_SEGMENT=ON \
  -DUSE_MNNVL=ON
make -j
sudo make install
```

两个开关都是必须的，缺一个 `MC_STORE_VRAM_FABRIC` 就不生效（只会打 WARNING）：

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `USE_VRAM_SEGMENT` | OFF | segment 用显存而非 host DRAM。会自动带上 `USE_CUDA=ON` |
| `USE_MNNVL` | OFF | 编入 `NvlinkTransport`（跨机 NVLink）。同样自动带 `USE_CUDA=ON` |

**互斥约束**：`USE_MNNVL` 不能与 `USE_HIP` / `USE_MUSA` / `USE_UBSHMEM` 同时开。
这些组合下 `gpu_vendor/mnnvl.h` 会分发到别的厂商后端，而那些后端没有带对齐的
fabric 分配接口，`MC_STORE_VRAM_FABRIC` 会降级为 `cudaMalloc` 并打 WARNING。

需要 CUDA 12.1+，并把 CUDA 库加进搜索路径：

```bash
export LIBRARY_PATH=/usr/local/cuda/lib64:$LIBRARY_PATH
export LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH
```

### 1.4 容易搞混的两个 NVLink 开关

| 开关 | 协议名 | 范围 | 机制 |
| --- | --- | --- | --- |
| `USE_MNNVL` | `nvlink` | **跨机**（同一 NVLink 域 / 同机架 18 台） | fabric handle（`cuMemCreate` + `CU_MEM_HANDLE_TYPE_FABRIC`） |
| `USE_INTRA_NVLINK` | `nvlink_intra` | **仅单机内** | CUDA IPC handle（`cudaIpcGetMemHandle`） |

本方案要的是 `USE_MNNVL`。`nvlink_intra` 名字里虽然有 "FabricMemory"
（`allocateFabricMemory_intra` 宏），实现其实是纯 `cudaMalloc`，
日志会明说 "memory will NOT be exportable"，**跨机用不了**。

### 1.5 验证编译结果

```bash
cd build
# 确认开关生效（cmake 输出里应有这几行）
cmake .. 2>&1 | grep -E 'VRAM SEGMENT is ON|Multi-Node NVLink support is enabled|CUDA support is enabled'

# 跑本次新增的配置开关单测
ctest -R vram_fabric_config_test --output-on-failure
# 机架相关单测
ctest -R 'replica_selection_test|segment_test' --output-on-failure
```

> 这些 C++ 单测**未在开发机执行过**（缺 glog / boost / ylt / tl::expected 且无 apt 源）。
> 首次部署时请务必跑一遍，别假定它们通过。

Python 侧可直接跑：

```bash
cd python && python3 -m unittest tests.unit.test_mooncake_config
```

## 2. 部署拓扑

### 2.1 角色划分

```
                         ┌─────────────┐
                         │   master    │  1 个（或 HA 多副本）
                         │  :50051     │  无需机架配置
                         └──────┬──────┘
                                │ 汇报 segment.rack_id
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
   ┌────┴────┐            ┌─────┴────┐            ┌─────┴────┐
   │ rack0   │            │ rack1    │    ...     │ rack3    │
   │ 18 节点 │            │ 18 节点  │            │ 18 节点  │
   └─────────┘            └──────────┘            └──────────┘
    每节点可同时是 prefill / decode / store
```

**`rack_id` 的划分必须与 NVLink 域（IMEX domain）边界完全一致。**
一个 NVL72 机架 = 一个 NVLink 域 = 一个 `rack_id`。
不要按物理机柜位置划分，也不要让一个 `rack_id` 跨越两个 NVLink 域——
那会让 master 以为两组节点之间有 NVLink，而实际没有。

### 2.2 端口

| 服务 | 默认端口 | flag |
| --- | --- | --- |
| master RPC | 50051 | `--port` |
| master metrics（HTTP） | 9003 | `--metrics_port` |
| store service REST API | 8080 | `--port` |
| client HTTP server | 9300 | `client_http_port`（配置项） |

### 2.3 启动 master

master **不需要**任何机架配置，它从各 segment 上报的 `rack_id` 自动建索引。

```bash
mooncake_master \
  --port=50051 \
  --metrics_port=9003 \
  --v=1                      # 打开 VLOG(1) 才能看到放置决策
```

HA 部署加 `--enable_ha=true`，并按 `STORE_USE_ETCD` / `STORE_USE_REDIS`
编译选项准备对应后端。

### 2.4 启动 store 节点

```bash
export MOONCAKE_CONFIG_PATH=/etc/mooncake/mooncake.json
python3 -m mooncake.mooncake_store_service --config /etc/mooncake/mooncake.json
```

也可以用 `-D` 覆盖单项，适合同一份配置分发到多机后只改机架号：

```bash
python3 -m mooncake.mooncake_store_service \
  --config /etc/mooncake/mooncake.json \
  -Drack_id=rack0 \
  -Dlocal_hostname=node-r0-03
```

## 3. 配置

### 3.1 配置优先级

```
配置文件（MOONCAKE_CONFIG_PATH 或 --config）  >  环境变量
```

两套机制不要混用。同时设了配置文件和环境变量时，环境变量**不会**生效——
`load_from_env()` 只在没有配置文件时才走。

### 3.2 机架相关配置项

| 配置文件字段 | 环境变量 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `rack_id` | `MOONCAKE_RACK_ID` | string | `""` | 所在 NVLink 域标识。空 = 关闭机架感知 |
| `strict_rack` | `MOONCAKE_STRICT_RACK` | bool | `false` | 写入是否硬约束在本机架 |

`strict_rack` 的布尔解析接受 `true/false/1/0/yes/no`（大小写不敏感）。

**`rack_id` 必须在 mount segment 之前设好**。代码里
`SetRackAffinity()` 在 `setup_internal` 中于建 client 之后、mount 之前调用；
如果通过别的路径延后设置，segment 会带不上机架身份，
master 侧 `RackSegmentIndex` 里就没有这个节点，整套机制静默失效。

`strict_rack=true` 但 `rack_id` 为空时，会打 WARNING 并退回非 strict，
不会静默改变放置行为。

### 3.3 按角色配置

#### Store 节点（**必配，这是数据来源**）

```jsonc
// /etc/mooncake/mooncake.json
{
  "local_hostname": "node-r0-03",
  "metadata_server": "P2PHANDSHAKE",
  "master_server_address": "10.0.0.1:50051",
  "protocol": "rdma",
  "device_name": "mlx5_0",
  "global_segment_size": "64gb",
  "local_buffer_size": "2gb",
  "rack_id": "rack0"
  // store 不是写入方，不需要 strict_rack
}
```

store 节点 mount 的 segment 靠 `rack_id` 进入 master 的索引。
**这一项省掉，机架感知就完全不工作**——master 会认为所有 segment 都没有机架身份。

#### Prefill 节点（写入侧：strict）

```bash
export MOONCAKE_RACK_ID=rack0        # 按所在机架填
export MOONCAKE_STRICT_RACK=true
```

语义：master 只在 rack0 的 store 节点上分配副本。rack0 容量不足时
触发淘汰并返回 `NO_AVAILABLE_HANDLE`，**不会**写到 rack1–3。

⚠️ **副本数约束**：`strict_rack=true` 时 `replica_num` 不能超过
**本机架**可服务的 segment 数，否则分配必然失败。

#### Decode 节点（读取侧：软偏好）

```bash
export MOONCAKE_RACK_ID=rack0        # 按所在机架填
export MOONCAKE_STRICT_RACK=false    # 或干脆不设
```

语义：优先挑同机架副本；同机架没有就读其他机架（走 RDMA）。

**decode 侧不要开 strict。** strict 只影响写入放置，在 decode 上开它没有收益，
而且当 decode 自身也做写入时（例如 chunked prefill 回填），会意外限制放置。

### 3.4 读取优先级（实际行为）

```
local MEMORY > local NOF_SSD > 同机架 MEMORY > 远端 MEMORY > 远端 NOF_SSD > LOCAL_DISK > DFS > DISK
```

两点容易误判：

1. **本地 NOF_SSD 仍然优先于同机架 MEMORY。** 这沿用机架感知之前的既有行为，
   本次没改。在 GB300 上这个顺序其实值得重新考虑（同机架 NVLink DRAM 约
   900 GB/s 量级，本地 NVMe 约 10 GB/s 量级），但那是一个独立决策，
   需要单独改动，目前**未做**。
2. **没有 `rack_id` 的副本被当成远端。** 所以老版本 master 或未配置机架的节点
   行为完全不变，机架感知是纯 opt-in；`rack_id` 为空时逐字节等价于历史行为。

### 3.5 fabric handle 开关（谨慎）

```bash
export MC_STORE_VRAM_FABRIC=1
```

生效需要**三个条件同时满足**，缺任何一个都会降级为 `cudaMalloc`：

1. 编译期 `USE_VRAM_SEGMENT=ON` **且** `USE_MNNVL=ON`（且未开 HIP/MUSA/UBSHMEM）
2. 运行时 `protocol == "nvlink"`
3. `MC_STORE_VRAM_FABRIC` 解析为真

取值语义：

| 取值 | 结果 |
| --- | --- |
| `1` / `true` / `yes` / `on` / `enable`（大小写不敏感，容忍首尾空格） | 开启 |
| `0` / `false` / `no` / `off` / `disable` | 关闭 |
| 空字符串、`maybe` 等无法解析的值 | 关闭 + WARNING 回显原值 |
| 未设置 | 关闭 |

⚠️ **与 `MC_STORE_USE_HUGEPAGE` 语义不同**：后者「存在即生效」，设成 `0` 也算开；
前者是**按值判断**，设成 `0` 就是关。这样设计是因为，如果 `=0` 被当成开启，
它选中的失败模式恰好是「注册成功但什么都没注册」的静默故障，
要等到远端读不到数据才暴露。

#### 必须避开的配置冲突

`MC_STORE_USE_HUGEPAGE` **绝对不能设**。分配路径的优先级是：

```
numa segments  >  ascend/ubshmem  >  hugepage  >  allocate_buffer_allocator_memory
                                      ↑                        ↑
                                  会在这里被截走          只有这条能到 VRAM
```

而 `MC_STORE_USE_HUGEPAGE` 是**存在即生效**的，设成 `0` 或空字符串同样会打开
hugepage 路径，从而让请求到不了 VRAM 分配。同理也要避免触发 NUMA 分段
（`protocol=="rdma"` 且检测到多个 NIC NUMA 节点时触发，日志有
`NUMA-segmented mode: NIC NUMA nodes=[...]`）。

#### 失败行为

fabric 分配失败时**直接报错，不静默回落**：

```
VRAM Segment fabric allocation failed for <N> bytes. Check that every device
reports fabric handle support and that an IMEX domain is configured, or unset
MC_STORE_VRAM_FABRIC to fall back to cudaMalloc.
```

这是刻意的：静默回落会复现这个功能本身要消除的隐形故障。
如果编译组合压根不支持该开关，会打这条 WARNING 然后按 `cudaMalloc` 继续：

```
MC_STORE_VRAM_FABRIC is set but this build provides no alignment-aware fabric
allocator (needs USE_MNNVL without USE_HIP/USE_MUSA/USE_UBSHMEM). Falling back
to cudaMalloc: the segment will NOT be reachable over NVLink from another node.
```

## 4. 上线验证

### 4.1 机架感知是否生效

master 端打开 `--v=1`，观察放置决策日志：

```
# strict 模式
key=..., rack_id=rack0, strict_rack_excluded=54, rack_serving_segments=18
# soft 模式
key=..., rack_id=rack0, rack_preferred_segments=18
```

`strict_rack_excluded=54` 对应 4 机架共 72 节点里排除掉的 54 个非本机架 segment，
`rack_serving_segments=18` 对应本机架的 18 个。这两个数字对不上，
说明 `rack_id` 划分与实际拓扑不一致。

逐项自检：

- 每个 store 节点都配了 `rack_id`，且同机架 18 台**完全相同**
- 4 个 `rack_id` 互不相同，且边界与 NVLink 域一致
- prefill 的 `replica_num` ≤ 本机架可服务 segment 数

### 4.2 fabric handle 是否生效

**成功**的标志是这条 INFO：

```
VRAM Segment allocated <N> bytes as an exportable fabric allocation, base=0x..., alignment=16777216
```

**失败**的标志是这条 WARNING（来自 `NvlinkTransport::registerLocalMemory`）：

```
Memory region 0x... is not allocated by cuMemCreate, but it can be used as local buffer
```

⚠️ 这条 WARNING 是**整套机制最危险的地方**：出现它时 `registerLocalMemory`
会 `return 0`，也就是注册「成功」但实际什么都没注册。
mount 不报错、启动看起来正常，但这块 buffer 根本没进 fabric，
远端永远拿不到数据——**只能靠这条日志发现**。部署后请务必 grep 一次。

### 4.3 真机（NVL72）上必须确认的项

这些在开发机上无法验证，必须上真机：

- `CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED` 在**全部** GPU 上为真。
  否则 `supportFabricMem()` 返回 false，静默回落 `cudaMalloc`。
- IMEX domain 覆盖整个 NVL72 机架的 18 个节点，且与 `rack_id` 划分一致。
- **未设** `MC_USE_NVLINK_IPC`——一旦设置，`supportFabricMem()` 直接返回 false，
  fabric 路径整体失效。
- `cuMemGetAllocationGranularity` 的实际取值。代码里按
  `max(granularity, 16MB)` 处理对齐（cachelib 的 `Slab::kSize` 要求），
  granularity 远大于 16 MB 时实际映射量会超过配置的 `global_segment_size`，
  需要留出余量。

## 5. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 放置完全没有机架偏好 | store 节点没配 `rack_id` | master 的索引空的，见 3.3 |
| 写入报 `NO_AVAILABLE_HANDLE` | strict 模式下本机架容量不足，或 `replica_num` 超过本机架 segment 数 | 扩本机架容量，或降 `replica_num`，或关 strict |
| 环境变量不生效 | 同时存在配置文件 | 配置文件优先，环境变量被忽略，见 3.1 |
| `MC_STORE_VRAM_FABRIC=1` 没反应 | 编译缺 `USE_MNNVL`/`USE_VRAM_SEGMENT`，或 `protocol != nvlink` | 看 WARNING 提示，见 3.5 |
| 日志有 `is not allocated by cuMemCreate` | 内存不是 fabric 分配的，注册了个空 | 见 4.2，这是静默故障 |
| 日志有 `NUMA-segmented mode` | 触发了 NUMA 分段，到不了 VRAM 路径 | 见 3.5 的配置冲突 |
| 跨机架读取失败且不回落 | **选路层未实现机架门控** | 这是已知限制，见 §0；跨机架请勿启用 fabric |

## 6. 当前实现边界

明确列一下**还没做**的部分，避免误判能力（详见 `20260918.md` §8.4）：

| 项 | 状态 |
| --- | --- |
| 机架感知放置（master strict/soft + reader 同机架优先） | 已实现 |
| segment 导出 fabric handle（分配 / 释放 / 对齐） | 已实现，带开关 |
| `protocol_priority()` 加入 `nvlink` 条目 | **未实现**（当前 nvlink 落到 0，rdma 是 2，永远选不到 NVLink） |
| nvlink 的机架可达性门控 | **未实现**（跨机架会误选 NVLink 且不回落） |
| 双 transport 并存（`"nvlink,rdma"` + `ENABLE_MULTI_PROTOCOL`） | **未实现**（当前 transport 安装是互斥 if/else） |
| host DRAM 走 EGM（路线 B） | 未实现 |

结论：**目前不要指望 NVLink 真正进入跨机架数据路径。**
机架感知放置可以上线并立即获益；fabric handle 仅限单机架验证。
