4 × GB300 NVL72 机架感知部署

72 台机器，4 个 NVL72 机架。逻辑上有 master、store server、client 三个角色， 但产物只有一个 wheel——构建一次，三边装同一个包，区别在启动命令和配置。 本文讲每个角色怎么构建、怎么配、数据怎么走。

01

三个角色，一个 wheel

先破除一个容易产生的误解：不需要分别构建三份东西。 mooncake_master 二进制、store.so、engine.so 都打进同一个 wheel（scripts/build_wheel.sh:63 拷 master 二进制）。

角色用 wheel 里的什么需要 GPU 编译开关机架配置
master mooncake_master 二进制 不需要 只管元数据，不链接 CUDA 无。从各 segment 上报的 rack_id 自动建索引
store server store.so + engine.so 仅验证 fabric 时需要 rack_id 必填，这是整套机制的数据来源
client store.so + engine.so 不需要 只分配 local_buffer rack_id + strict_rack（prefill 开、decode 不开）

GPU 开关（USE_VRAM_SEGMENT + USE_MNNVL）是编译期的， 所以一旦打开，三边装的都是带开关的同一个包。但它只对 store server 有意义—— 分配 global_segment 的是它。client 侧只分配 local_buffer， 不走 VRAM 分支。

02

架构：控制面全局，数据面按机架

master 是全局单点（或 HA 多副本），与 72 个节点都通信，但只走控制面—— 元数据和放置决策。真正的 KV 数据完全不经过它。

控制面（元数据，不传数据） 机架内 NVLink 域 跨机架 RDMA

rack_id 不是物理机柜位置。 它是 NVLink 域（IMEX domain）标识。一个 NVL72 机架 = 一个 NVLink 域 = 一个 rack_id。 让一个 rack_id 跨越两个 NVLink 域，会让 master 以为两组节点间有 NVLink，实际没有。

03

PD 访问路径：写是硬约束，读是软偏好

这是整套方案的核心语义差异。prefill 写入不允许跨机架， decode 读取优先同机架但跨机架也必须能读——否则副本在别的机架就会失败。

决策位置

写入：master 侧

MasterService::AllocateReplicas 把非本机架 segment 放入 excluded_segments。客户端无从绕过。

决策位置

读取：客户端侧

SelectBestReplica 在客户端进程内按 local_rack_id 排序。 master 不参与筛选。

兼容性

纯 opt-in

rack_id 为空时逐字节等价于历史行为。 未配置机架的节点、老版本 master 都不受影响。

04

怎么构建

两个场景。先判断你要不要 fabric handle——大多数情况下不要， 机架感知本身不需要任何 GPU 编译开关。

场景cmake 开关Dockerfile适用
A. 只要机架感知 无需开关 docker/mooncake.Dockerfile（现成的，一行不改） 推荐先做。收益确定，风险低
B. 加 fabric handle -DUSE_VRAM_SEGMENT=ON
-DUSE_MNNVL=ON		 ppio/mooncake-rack.Dockerfile 仅在隔离节点验证 NVLink 分配侧

场景 A · 一次构建，三边通用

sudo bash dependencies.sh -y

mkdir -p build && cd build
cmake .. -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build .
cd ..

OUTPUT_DIR=dist ./scripts/build_wheel.sh
# 产物：mooncake-wheel/dist/*.whl
#   含 mooncake_master 二进制、store.so、engine.so、python 包

场景 B · 加两个开关

cmake .. -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DUSE_VRAM_SEGMENT=ON \
  -DUSE_MNNVL=ON

# cmake 输出必须有这三行，否则开关没生效：
#   -- VRAM SEGMENT is ON
#   -- Multi-Node NVLink support is enabled
#   -- CUDA support is enabled

两个开关各自都会强制 USE_CUDA=ON。 互斥约束：USE_MNNVL 不能与 USE_HIP / USE_MUSA / USE_UBSHMEM 同开—— 那些组合会分发到没有对齐 fabric 接口的厂商后端，开关降级为 cudaMalloc 并打 WARNING。

容器

# 场景 A
docker build -f docker/mooncake.Dockerfile -t mooncake:base .

# 场景 B —— 注意从仓库根执行，构建上下文必须是仓库根
docker build -f ppio/mooncake-rack.Dockerfile -t mooncake:rack-arm64 .

GB300 是 Grace，aarch64。 镜像必须在 arm64 机器上构建，x86_64 镜像跑不起来。 跨平台构建需要 qemu，很慢，只适合应急： docker buildx build --platform linux/arm64 ...

ppio/mooncake-rack.Dockerfile 与原版的四处差异

差异为什么
加 USE_VRAM_SEGMENT + USE_MNNVL 两者缺一，MC_STORE_VRAM_FABRIC 就不生效
cmake 后 grep 三行 STATUS，不符则构建失败 否则这种错配要等到运行时、甚至等到远端读不到数据才暴露
BUILD_UNIT_TESTS=ON 且 builder 阶段跑 ctest 这几个用例此前从未在有依赖的环境执行过，镜像构建是第一次真跑。--build-arg RUN_TESTS=0 可跳过
去掉 WITH_EP=ON EP/PG 扩展与机架无关，会拉 torch，构建时间约翻倍

nvlink_allocator.so 缺失不影响本方案。 它只被 mooncake-integration/allocator.py 用作推理框架侧的 torch 可插拔分配器；store 的 fabric 分配走 NvlinkTransport::allocatePinnedLocalMemory，编在 engine.so 里。 构建日志里那句 "likely ARM64" 只是文案推测，build.sh 里并没有架构门控。

05

怎么配置

先记一条优先级规则，它是最容易踩的坑： 配置文件优先于环境变量。两者同时存在时环境变量不生效—— load_from_env() 只在没有配置文件时才走。 设了 MOONCAKE_RACK_ID 却又指了 --config，机架感知静默失效。

master  不需要任何机架配置

它从各 segment mount 时上报的 rack_id 自动建 RackSegmentIndex。 

mooncake_master \
  --port=50051 \
  --metrics_port=9003 \
  --v=1              # 必须开，否则看不到放置决策日志
flag默认NVL72 建议
--port50051保持
--metrics_port9003保持
--v0设 1，否则无放置日志
--enable_hafalse72 节点规模建议开，需 etcd/redis 后端

store server  rack_id 必填，这是数据来源

省掉这一项，master 的索引就是空的，整套机架感知完全不工作。 18 台共用一份配置，只改 local_hostname。 

// /etc/mooncake/store.json
{
  "local_hostname": "node-r0-03",
  "metadata_server": "P2PHANDSHAKE",
  "master_server_address": "10.0.0.1:50051",
  "protocol": "rdma",
  "device_name": "mlx5_0",
  "global_segment_size": "64gb",
  "local_buffer_size": "2gb",
  "rack_id": "rack0",
  "enable_client_http_server": true,
  "client_http_port": 9300
  // store server 不是写入方，不需要 strict_rack
}
python3 -m mooncake.mooncake_store_service \
  --config /etc/mooncake/store.json \
  --port 8080 \
  -Dlocal_hostname=node-r0-03 \
  -Drack_id=rack0              # -D 覆盖单项，适合一份配置分发 72 台

prefill  写入侧，开 strict

export MOONCAKE_RACK_ID=rack0        # 按所在机架
export MOONCAKE_STRICT_RACK=true

语义：master 只在 rack0 的 store server 上分配副本。 rack0 不足时触发淘汰并返回 NO_AVAILABLE_HANDLE，不会写到 rack1–3。

副本数约束：strict_rack=true 时 replica_num 不能超过本机架可服务 segment 数（这里是 18）， 否则分配必然失败。

decode  读取侧，不开 strict

export MOONCAKE_RACK_ID=rack0        # 按所在机架
export MOONCAKE_STRICT_RACK=false    # 或干脆不设

decode 不要开 strict。strict 只影响写入放置， 在 decode 上开它没有收益，而且当 decode 自身也做写入时 （例如 chunked prefill 回填）会意外限制放置。

rack_id 划分

机架rack_id节点
NVL72 #0rack0node-r0-01 … node-r0-18
NVL72 #1rack1node-r1-01 … node-r1-18
NVL72 #2rack2node-r2-01 … node-r2-18
NVL72 #3rack3node-r3-01 … node-r3-18

同机架 18 台的 rack_id 必须完全相同，4 个机架互不相同。 rack_id 必须在 mount segment 之前设好—— SetRackAffinity() 在建 client 之后、mount 之前调用。

06

不要设的环境变量

这四个每一个都会让方案静默失效或直接不可用。

变量后果
MC_STORE_USE_HUGEPAGE 存在即生效（设 0 也算开）。 分配在到达 VRAM 路径前被 hugepage 截走，fabric 开关等于没开
MC_USE_NVLINK_IPC supportFabricMem() 直接 return false，静默回落 cudaMalloc
MC_FORCE_MNNVL 会让该节点彻底没有 RDMA，见下方死结
MC_INTRANODE_NVLINK 只装 nvlink_intra（单机 CUDA IPC），跨机完全不通

07

上线验证

机架感知是否生效

master 开 --v=1，看放置决策日志： 

# strict 模式
key=..., rack_id=rack0, strict_rack_excluded=54, rack_serving_segments=18
# soft 模式
key=..., rack_id=rack0, rack_preferred_segments=18

54 = 72 节点里排除的非本机架 segment，18 = 本机架的。 这两个数字对不上，说明 rack_id 划分与实际拓扑不一致。

整套机制最危险的日志（来自 NvlinkTransport::registerLocalMemory）：

Memory region 0x... is not allocated by cuMemCreate, but it can be used as local buffer

出现它时 registerLocalMemory 会 return 0—— 注册「成功」但实际什么都没注册。mount 不报错、启动看起来正常， 但这块 buffer 根本没进 fabric，远端永远拿不到数据。 只能靠这条日志发现，部署后务必 grep 一次。

真机（NVL72）必须确认

项不满足的后果
CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED 在全部 GPU 上为真 supportFabricMem() 返回 false，静默回落 cudaMalloc
IMEX domain 覆盖整个 NVL72 的 18 个节点，且与 rack_id 一致 fabric 分配失败或跨节点不可达
容器已透传 IMEX channel 设备节点 cuMemCreate 的 fabric 分配失败
cuMemGetAllocationGranularity 的实际取值 代码按 max(granularity, 16MB) 对齐；granularity 远大于 16 MB 时实际映射量会超过配置的 global_segment_size，需留余量

IMEX 设备路径 /dev/nvidia-caps-imex-channels 是按 NVIDIA 驱动惯例给的， 未在真机核对。上机前先 ls 确认。

08

当前能力边界

明确列出还没做的部分，避免误判能力。

项状态
机架感知放置（master strict/soft + reader 同机架优先） 已实现 可直接上线
segment 导出 fabric handle（分配 / 释放 / 对齐） 已实现 带开关，仅隔离节点验证
protocol_priority() 加入 nvlink 条目 未实现 nvlink 落到 0，rdma 是 2，永远选不到
nvlink 的机架可达性门控 未实现 跨机架会误选 NVLink 且不回落
双 transport 并存（"nvlink,rdma"） 未实现 当前安装是互斥 if/else
host DRAM 走 EGM 未实现
本地 NOF_SSD vs 同机架 MEMORY 优先级 待决策 当前 SSD 优先，GB300 上可能不合理

机架感知放置可以上线并立即获益。 即使完全不启用 NVLink，把写入锁在同机架内也值得做—— 同机架 RDMA 通常只经过一级 leaf 交换机，避免了 spine 跳数和跨机架拥塞。 fabric handle 仅限单机架隔离验证。
